# To-Do List Service

## 1. Service Description

A small REST service for managing to-do items. Each item has:

| Field              | JSON name          | Notes                                         |
|--------------------|--------------------|-----------------------------------------------|
| id                 | `id`               | UUID, generated by the service                |
| description        | `description`      | Required, trimmed, must not be blank          |
| status             | `status`           | `"not done"`, `"done"` or `"past due"`        |
| creation_datetime  | `creationDateTime` | Set by the service on creation                |
| due_datetime       | `dueDateTime`      | Required, must be in the future on creation   |
| done_datetime      | `doneDateTime`     | Set when marked done, cleared when marked not done |

Items are stored in an in-memory H2 database (columns use the snake_case names above).

### API

Base path: `/api/toDoItems`

| Action                    | Method & Path                     | Body                                                      |
|---------------------------|-----------------------------------|-----------------------------------------------------------|
| Add an item               | `POST /addItem`                   | `{"description": "...", "dueDateTime": "2030-01-01T10:00:00"}` |
| Update description        | `PATCH /{id}/updateDescription`   | `{"description": "..."}`                                  |
| Mark as done              | `PATCH /{id}/MarkDone`            | –                                                         |
| Mark as not done          | `PATCH /{id}/MarkNotdone`         | –                                                         |
| Get an item               | `GET /{id}/getItem`               | –                                                         |
| Get "not done" items      | `GET /getAllItems`                | –                                                         |
| Get all items (any status)| `GET /getAllItems?fetchAll=true`  | –                                                         |

Example item response:

```json
{
  "id": "1929ebeb-ed4d-462e-afdb-0baf662c7be8",
  "description": "Buy milk",
  "status": "not done",
  "creationDateTime": "2026-09-27T20:28:02.801",
  "dueDateTime": "2030-01-01T10:00:00",
  "doneDateTime": null
}
```

Errors are returned as JSON (`timestamp`, `status`, `error`, `message`, `path`):

- `400 Bad Request` – invalid input (blank description, missing/past due date, malformed id)
- `404 Not Found` – item does not exist
- `409 Conflict` – item is past due (immutable), or it was modified concurrently

Interactive API docs (Swagger UI) are available at `http://localhost:8080/swagger-ui.html` when the service is running.

### Automatic "past due" update

A scheduled job (`PastDueStatusScheduler`) runs at startup and then every 60 seconds
(configurable via `todo.past-due-check.interval` in `application.yaml`). It moves every
`"not done"` item whose `due_datetime` has passed to `"past due"` in a single bulk update.

### Assumptions

- **Immutability is enforced in real time, not only by the scheduler.** An item whose due date
  has passed is rejected with `409` even if the scheduler has not yet flipped it to `"past due"`.
  This closes the window between the due date passing and the next scheduler run. Until that run,
  the stored status is still `"not done"`, so `getItem` and `getAllItems?fetchAll=true` may briefly
  show `"not done"` for an item that already rejects changes as past due.
- **The status could also be corrected on access instead of waiting for the scheduler.** An
  alternative is to flip an overdue `"not done"` item to `"past due"` whenever it is read or an
  update is attempted, so the API always returns the correct status. This would need a conditional
  single-item update (`... WHERE id = :id AND status = 'not done' AND due_datetime < :now`) to avoid
  optimistic-lock clashes with the scheduler, and `noRollbackFor = ItemImmutableException.class` on
  the update methods so the flip is kept when the change is rejected. It was not implemented to keep
  reads side-effect free and the scheduler as the single place that changes status automatically.
- **`"done"` items stay editable after their due date.** Only `"not done"` items become past due
  (the scheduler only touches `"not done"` items). A done item whose due date has passed can still be
  edited or moved back to `"not done"`; once reopened it is overdue, so it is immediately treated as
  past due, rejects further changes, and is flipped to `"past due"` on the next scheduler run.
- The default "not done" listing only returns items that are still before their due date, so items
  that are overdue but not yet processed by the scheduler are not shown as "not done".
- Marking an item with the status it already has is a no-op and returns `200`.
- Timestamps are `LocalDateTime` (ISO-8601, no time zone) and are interpreted in the server's
  local time zone. The Docker image runs in UTC.
- Optimistic locking (`@Version`) protects against concurrent updates to the same item.
- `GET /{id}/getItem` returns the item wrapped in a single-element JSON array.
- Data is in-memory and is lost when the service stops.

### Design Decisions

- **`description` is not a unique constraint.** It is free text, not an identifier: items are
  identified by their UUID, and it is legitimate to have several items with the same description
  (e.g. "Buy milk" every week, or the same task with different due dates). A unique constraint
  would reject valid input and make descriptions of done or past-due items block new ones.
- **No caching is used.** It would add little here: the database is in-memory H2, so reads are
  already fast, and the data changes often (status updates, description edits, and the scheduler
  flipping items to "past due" in bulk). A cache would need invalidation on every one of those
  writes, including the scheduler's bulk update that bypasses entity-level events, adding
  complexity and a risk of serving stale status without a measurable benefit.

## 2. Tech Stack

- **Runtime:** Java 21
- **Framework:** Spring Boot 4.1 (Spring Web MVC, Spring Data JPA, Spring Scheduling)
- **Database:** H2 (in-memory)
- **Libraries:** Lombok, springdoc-openapi (Swagger UI)
- **Build:** Maven (via the included Maven Wrapper)
- **Testing:** JUnit 5, Mockito, Spring Boot Test / MockMvc, `@DataJpaTest`
- **Containerisation:** Docker (multi-stage build, Eclipse Temurin JRE 21)

## 3. How-To Guide

Prerequisites: JDK 21 for local builds, or just Docker for running in a container.
On Windows use `mvnw.cmd` instead of `./mvnw`.

### Build the service

```bash
./mvnw clean package
```

This compiles the code, runs the tests and produces `target/ToDoListService-0.0.1-SNAPSHOT.jar`.
Add `-DskipTests` to build without running the tests.

### Run the automatic tests

```bash
./mvnw test
```

The suite contains the following types of tests (all under `src/test/java/com/tradeBytes/toDoListService`):

| Type                    | Class                             | Setup                                     | What it covers |
|-------------------------|-----------------------------------|-------------------------------------------|----------------|
| Unit tests              | `service/TodoServiceTest`         | Plain JUnit 5 + Mockito (mocked repository) | Business rules: validation of description / due date, status transitions, immutability of past-due items (by status and by due date), reopening done items, not-found handling |
| Controller (web slice)  | `controller/ToDoControllerTest`   | `@WebMvcTest` + MockMvc, service mocked   | Request mapping, JSON (de)serialisation and HTTP status codes for every endpoint: `200`, `400` (bad input, malformed JSON, invalid UUID, non-boolean `fetchAll`), `404`, `409` (immutable item, concurrent modification) |
| Repository (JPA slice)  | `repository/ToDoItemRepositoryTest` | `@DataJpaTest` against H2               | Custom queries (fetching "not done" items, bulk past-due update and its version bump), status stored as its string value, optimistic locking on stale updates |
| Integration (end-to-end)| `ToDoListServiceIntegrationTest`  | `@SpringBootTest` + MockMvc, real H2      | Full item lifecycle through the API, and the `PastDueStatusScheduler` flagging overdue items which then reject changes |
| Concurrency             | `ToDoConcurrencyTest`             | `@SpringBootTest`, real H2, parallel threads | Race between the scheduler and a request, two writers editing the same item, and parallel edits where every successful commit counts and losers get an optimistic-lock error |

In the Spring Boot tests the scheduler interval is set to `1h` so it does not interfere; the tests
trigger it explicitly where needed.

### Run the service locally using Docker

```bash
docker build -t todo-list-service .
docker run --rm -p 8080:8080 todo-list-service
```

`--rm` removes the container when it stops, so the command can be re-run without a name clash.

The service is then available at `http://localhost:8080`. Example:

```bash
# Create an item
curl -X POST http://localhost:8080/api/toDoItems/addItem \
  -H "Content-Type: application/json" \
  -d '{"description": "Buy milk", "dueDateTime": "2030-01-01T10:00:00"}'

# List all items
curl "http://localhost:8080/api/toDoItems/getAllItems?fetchAll=true"
```

To run without Docker: `./mvnw spring-boot:run`.

Useful endpoints:
- Swagger UI: `http://localhost:8080/swagger-ui.html`
- H2 console: `http://localhost:8080/h2-console` (JDBC URL `jdbc:h2:mem:mydb`, user `sa`, password `password`)
